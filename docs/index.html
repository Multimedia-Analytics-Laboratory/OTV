One-Token Verification · Method, evidence, and implications
01 / The idea

Read the computation
that already exists.

OTV asks a simple question: can a reasoner’s own cached computation help assess its reasoning? A special [ToT] token queries that cache through a verification adapter, and a regression head maps the resulting representation to a score.

KV cacheReuses token-wise, layer-wise states from the frozen reasoner.
[ToT] + LoRALearns how to query those states in verification mode.
Regression headConverts the final probe state into a scalar in [0, 1].
Dense targetsTurn a final correctness label into supervision along the response.
02 / Where the keys and values come from

Reuse the old K/V.
Compute new K̃/Ṽ for each probe.

There are two distinct sources. The reasoner produces cached K and V with the verification adapter off. Each [ToT] probe produces its own new Q̃, K̃, and Ṽ with LoRA on. A probe reads its cached prefix and its own new K̃/Ṽ—never another probe’s K̃/Ṽ.

Q̃ᵢ = hᵢ(WQ + ΔWQ),   K̃ᵢ = hᵢ(WK + ΔWK),   Ṽᵢ = hᵢ(WV + ΔWV)
aᵢ = softmax(Q̃ᵢ [K1:t; K̃ᵢ]ᵀ / √d),   oᵢ = aᵢ [V1:t; Ṽᵢ]
Row-vector notation, i = t + 1. ΔW is the low-rank update. The first set of keys/values is cached; the final pair is newly produced for this probe.

A probe also creates a self-attention K̃/Ṽ pair, just as a single verification token would. This pair stays local to that probe; it does not modify the reasoner’s shared cache.

Why this parallelizes. Stack the probe queries into a matrix. The cache block has a triangular visibility mask; the new-probe block permits only the diagonal. No query consumes another query’s result, so all rows can run together at each layer. The resulting probe states continue through the remaining layers, and the head reads the final states.

One-token verification means one query for a chosen prefix. Scoring all prefixes still requires attention to many cached positions; batching reduces sequential dispatches, not the underlying dependencies of reasoning generation.

03 / What the verifier learns

One outcome.
Several possible confidence targets.

Let u be progress through the supervised response, and y its final correctness label. Most implemented target rules use r = 0.5 + (y − 0.5)f(u). The shape of f determines how the final label is distributed along the trace. Training minimizes mean squared error against these targets.

Linear is the default, not a token-level proof of correctness. A wrong solution can contain sound early steps, and a correct one can recover from a detour. The alternative curves change this supervision prior; their ranking value and calibration must be checked empirically.

05 / Related work

What does a verifier
get to read?

The central design choice is the evidence available to the verifier—and the computation needed to read it. These representative approaches make different trade-offs.

ApproachSignal & supervisionAdded verification work
DeepConf ↗Fu et al., 2025Token-distribution statistics, aggregated over local windows. No verifier training.Track confidence during decoding; no extra learned verifier pass.
Hidden-state probe ↗Zhang et al., 2025Selected hidden states; a small head learns intermediate-answer correctness.Read an existing representation and run the head; no new attention query.
Outcome verifier ↗Cobbe et al., 2021Question and candidate solution text; final-answer correctness labels.Run a trained verifier over each candidate solution.
Process verifier ↗Lightman et al., 2023Solution text; human correctness labels for individual reasoning steps.Run the reward model over the text to produce step scores.
GenRM-CoT ↗Zhang et al., 2024Candidate text; trains with next-token prediction on verification rationales and verdicts.Generate a verification rationale before the verdict; can sample several critiques.
OTV ↗Zhuang et al., 2026Token-wise, layer-wise cached K/V; dense targets derived from final correctness.One LoRA-enabled probe through the layers per queried prefix, plus a scalar head.

An architectural comparison, not a speed or accuracy ranking. Rows describe the linked papers; other process verifiers may use synthetic labels. OTV requires access to the reasoner’s internal cache and training for that backbone.

OTV’s trade-off. It adds a learned attention readout over cached computation, which is more work than confidence aggregation or a small probe. It avoids re-encoding the full solution text in a separate verifier and decoding a critique. Its token-wise training targets still come from final outcomes; they do not supply independently checked step labels.

07 / What follows & applications

From a confidence score
to a better next action.

OTV makes a reasoner’s existing computation available for learned verification. The next step is to turn that signal into better choices about what to continue, check, or stop.

Guide exploration with grounded feedback.

OTV could prioritize branches worth continuing in coding, theorem proving, or scientific search. Feedback from tests, formal checks, and simulations could then teach the verifier which uncertain paths can recover.

Evolve the verifier with the reasoner.

Updating the reasoner changes the cached representations and shared computation that its verifier relies on. Co-adapting the verification adapter and recalibrating its scores alongside new checkpoints could create a form of metacognition that evolves with the model’s own reasoning.

Read the structure of reasoning.

The KV cache retains token-wise, layer-wise states accumulated while a solution develops. Beyond a scalar score, learned queries could probe strategy changes, intermediate commitments, and recovery from detours, opening a research interface into how reasoning unfolds.
